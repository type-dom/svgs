## 📖 引言

上下文管理是与 AI Agent 协作的核心技能。良好的上下文管理能:

- ✅ 提高回答准确性
- ✅ 减少 token 消耗
- ✅ 保持对话连贯性
- ✅ 提升整体效率

本指南分享经过实践验证的上下文管理技巧。

## 🎯 理解上下文

### 什么是上下文？

```
上下文 = AI 理解任务所需的所有信息

包括:
• 对话历史 (之前的问答)
• 引用文档 (@引用的文件)
• 当前代码 (选中的代码片段)
• 项目背景 (工程自动感知)
• 明确的需求描述
```

### 上下文的重要性

```
充足且精准的上下文 → 准确的回答
模糊或缺失的上下文 → 低质量的回答

示例对比:

❌ 低效上下文:
"帮我写个组件"
→ AI 不知道：什么类型？什么规范？什么用途？

✅ 高效上下文:
【角色】TypeDom 专家
【任务】创建 StarSvg 组件
【参考】@技术栈.md @编码规范.md
【要求】viewBox: 0 0 1024 1024, 24x24 默认尺寸
【路径】M512 42.666667...
→ AI 清楚：所有必要信息
```

## 🔧 上下文管理策略

### 策略 1: 精准注入法

**核心原则**: 只注入必要的上下文，避免信息过载

**实施方法**:

```markdown
Step 1: 明确任务类型
- 代码生成？→ 引用编码规范 + 技术栈
- Bug 修复？→ 引用错误信息 + 相关代码
- 文档编写？→ 引用 API 文档 + 接口定义

Step 2: 选择相关文档 (3-5 篇为宜)
✅ 推荐:
@ai-docs/02-开发规范/编码规范.md
@ai-docs/01-项目概述/技术栈.md
@ai-docs/03-API 文档/接口定义.md

❌ 避免:
一次性引用 10+ 个文档
引用不相关的文档

Step 3: 提供关键代码片段
✅ 只选中相关的函数或类
❌ 不要选中整个文件
```

**效果对比**:

| 方法 | Token 消耗 | 准确率 | 响应速度 |
|-----|-----------|--------|---------|
| 精准注入 | ~2000 | 90%+ | 快 |
| 全部注入 | ~8000 | 70% | 慢 |

---

### 策略 2: 分层递进法

**核心原则**: 分层次提供上下文，由浅入深

**实施方法**:

```
Level 1: 基础上下文 (必须)
├─ 角色定位
├─ 任务描述
└─ 核心约束

Level 2: 支持上下文 (推荐)
├─ 相关文档引用
├─ 示例代码
└─ 背景信息

Level 3: 补充上下文 (可选)
├─ 历史对话记录
├─ 类似案例
└─ 特殊要求
```

**实际应用**:

```markdown
【Level 1 - 基础】
【角色】TypeDom Framework 专家
【任务】创建 HeartSvg 组件
【约束】遵循编码规范，使用 TypeScript 严格模式

[等待 AI 确认理解]

【Level 2 - 支持】
【参考】@编码规范.md @命名约定.md @技术栈.md
【示例】参考 AddSvg 组件的实现风格
【路径】M512 42.666667...

[AI 开始生成]

【Level 3 - 补充】
另外，这个组件会用于情人节专题，需要支持动画效果。
请在生成时考虑性能优化。
```

**优势**:
- ✅ AI 逐步深入理解
- ✅ 避免一次性信息过载
- ✅ 便于中途调整方向

---

### 策略 3: 动态维护法

**核心原则**: 根据对话进展动态调整上下文

**实施方法**:

```
对话初期:
• 提供完整背景
• 引用核心文档
• 明确目标和约束

对话中期:
• 聚焦具体问题
• 减少背景信息
• 保持上下文连贯

对话后期:
• 总结关键点
• 确认理解一致
• 清理无关上下文
```

**实际示例**:

```markdown
=== 对话初期 ===
【角色】你是@type-dom/svgs 项目的 AI 助手
【背景】项目基于 TypeDom Framework ^0.5.0，TypeScript 5.9.3+
【目标】帮助我创建一系列 SVG 图标组件
【规范】严格遵守 @编码规范.md 和 @命名约定.md

=== 对话中期 (第 3 个组件) ===
继续创建下一个组件：MoonSvg
【路径】M512 42.666667...
【要求】与之前的 StarSvg 保持一致的风格
(不需要重复说明项目背景和规范)

=== 对话后期 ===
好的，今天创建的 5 个组件都已完成：
✓ StarSvg ✓ HeartSvg ✓ MoonSvg ✓ SunSvg ✓ CloudSvg
接下来请帮我：
1. 批量添加 JSDoc 注释
2. 生成统一的测试文件
3. 更新导出配置
```

## 💡 实用技巧

### 技巧 1: 上下文字面量 (Context Literal)

**方法**: 用简洁的语言概括上下文

```markdown
❌ 冗长:
"我之前跟你说过我们项目是用 TypeDom Framework 的，
然后我们的编码规范是在 ai-docs/02-开发规范/编码规范.md 
这个文件里面，里面有详细的命名规则..."

✅ 简洁:
【上下文】TypeDom 项目，规范：@编码规范.md
```

**效果**: 节省 60-70% token

---

### 技巧 2: 上下文锚点 (Context Anchor)

**方法**: 用标签或标记快速定位上下文

```markdown
【项目背景】#type-dom #svg #typescript-strict
【任务类型】#component-generation #unit-test
【参考文档】#coding-standard #naming-convention
【优先级】#high-priority #production-ready

这些标签帮助 AI 快速识别上下文类型
```

**优势**:
- ✅ AI 快速分类
- ✅ 便于后续检索
- ✅ 节省描述时间

---

### 技巧 3: 上下文继承 (Context Inheritance)

**方法**: 利用对话历史自动继承上下文

```markdown
第一轮:
【项目】@type-dom/svgs
【规范】@编码规范.md
【任务】创建 StarSvg

第二轮 (自动继承):
继续创建 MoonSvg
(无需重复说明项目和规范)

第三轮 (显式继承):
基于上面的组件风格，再创建 SunSvg
并添加完整的 JSDoc 注释
```

**注意事项**:
- ✅ 短期对话 (10 轮内) 可依赖自动继承
- ❌ 长期对话需定期重申关键上下文
- ⚠️ 切换话题时需明确说明

---

### 技巧 4: 上下文摘要 (Context Summarization)

**方法**: 定期总结对话要点，刷新上下文

```markdown
【对话摘要】
已完成的:
✓ StarSvg 组件 + 测试
✓ HeartSvg 组件 + 测试
✓ 讨论了颜色方案 (currentColor)

待完成的:
□ MoonSvg 组件 (进行中)
□ SunSvg 组件
□ 批量添加文档注释

【下一步】
现在请为 MoonSvg 添加动画效果支持
```

**优势**:
- ✅ 清除无关历史
- ✅ 聚焦当前任务
- ✅ 防止上下文漂移

---

### 技巧 5: 上下文隔离 (Context Isolation)

**方法**: 不同话题使用独立对话

```
场景：同时处理多个任务

❌ 错误做法 (混在一起):
对话 #1: 创建 StarSvg 组件
对话 #1: 修复 UserSvg 的 Bug
对话 #1: 讨论项目架构
→ 上下文混乱，AI 容易混淆

✅ 正确做法 (隔离):
对话 A: [SVG 组件开发]
  - StarSvg
  - MoonSvg
  - SunSvg

对话 B: [Bug 修复]
  - UserSvg 问题
  - CloseSvg 问题

对话 C: [架构讨论]
  - 目录结构优化
  - 导出策略调整
```

**工具支持**:
- 使用不同的聊天窗口
- 给对话命名和标记
- 定期归档旧对话

## 📊 Token 优化策略

### Token 消耗分析

```
典型对话的 Token 分布:

上下文引用：40-60%
对话历史：20-30%
AI 回答：20-30%

优化空间巨大!
```

### 优化方法

#### 方法 1: 精简文档引用

```markdown
❌ 低效:
@ai-docs/01-项目概述/项目背景.md
@ai-docs/01-项目概述/技术栈.md
@ai-docs/01-项目概述/架构图.md
@ai-docs/02-开发规范/编码规范.md
@ai-docs/02-开发规范/命名约定.md
@ai-docs/02-开发规范/代码审查清单.md
@ai-docs/02-开发规范/测试规范.md
@ai-docs/03-API 文档/接口定义.md
@ai-docs/03-API 文档/数据模型.md
(9 个文档，~4000 tokens)

✅ 高效:
【核心参考】@编码规范.md @技术栈.md
(2 个文档，~800 tokens)

说明：AI 会自动从索引中检索相关信息
```

**节省**: 70-80% token

#### 方法 2: 选择性代码引用

```markdown
❌ 低效:
粘贴整个文件 (500 行)

✅ 高效:
只选中相关函数 (20-50 行)

【问题】第 25-35 行的 mount 方法
```typescript
[只粘贴这 10 行代码]
```
```

**节省**: 80-90% token

#### 方法 3: 复用历史上下文

```markdown
第一轮 (详细说明):
【项目】@type-dom/svgs - TypeDom SVG 组件库
【技术栈】TypeScript 5.9.3+, TypeDom ^0.5.0
【规范】@编码规范.md - 严格模式，PascalCase 命名
【任务】创建 StarSvg 组件

第十轮 (复用历史):
继续创建 MoonSvg，同样要求
(自动继承之前的上下文)

**节省**: 50-60% token per turn
```

## 🚨 常见问题

### 问题 1: AI 忘记之前的上下文

**症状**:
```
AI 说："我不记得之前提到过..."
或者重复询问已经提供的信息
```

**原因**:
- 对话轮次过多 (>20 轮)
- 上下文被截断
- 话题切换未明确说明

**解决方案**:
```markdown
方案 1: 主动提醒
"回顾一下我们之前的对话，我正在..."

方案 2: 提供摘要
【上下文摘要】
之前已完成：StarSvg, HeartSvg
正在进行：MoonSvg
使用的规范：@编码规范.md

方案 3: 开启新对话
"让我们重新开始，先总结一下..."
```

---

### 问题 2: AI 误解上下文

**症状**:
```
AI 生成的代码不符合要求
AI 引用了错误的文档
AI 理解了字面但没理解意图
```

**原因**:
- 上下文模糊不清
- 引用了不相关的文档
- 缺少关键信息

**解决方案**:
```markdown
方案 1: 澄清意图
"我的意思是...，请重新理解"

方案 2: 提供更具体的示例
"像这样：[示例代码]"

方案 3: 明确指出错误
"你引用的文档不对，应该是@编码规范.md"
```

---

### 问题 3: 上下文过多导致响应慢

**症状**:
```
AI 响应时间明显变长 (>5 秒)
回答质量下降
AI 似乎"迷失"在上下文中
```

**原因**:
- 引用文档过多 (>10 个)
- 对话历史过长 (>50 轮)
- 粘贴代码过多 (>500 行)

**解决方案**:
```markdown
方案 1: 精简上下文
只保留最相关的 3-5 个文档

方案 2: 分段对话
将大任务拆分为多个小对话

方案 3: 使用摘要
用简短摘要代替完整历史
```

## 🎯 最佳实践清单

### ✅ 应该做的

```
□ 开场明确角色和任务
□ 引用 3-5 个核心文档
□ 提供关键代码片段 (而非全文)
□ 使用结构化提示词
□ 定期总结对话要点
□ 不同话题分开对话
□ 及时给予反馈
□ 保存常用上下文模板
```

### ❌ 不应该做的

```
□ 一次引用 10+ 个文档
□ 粘贴整个文件
□ 假设 AI 知道一切
□ 频繁切换话题
□ 使用模糊的描述
□ 忽略 AI 的澄清请求
□ 在不相关对话中继续
□ 重复提供相同信息
```

## 📚 进阶技巧

### 技巧 1: 元上下文 (Meta-Context)

**方法**: 告诉 AI 如何理解上下文

```markdown
【阅读指南】
请按以下优先级理解我的需求:
1. 业务逻辑 > 技术实现
2. 用户体验 > 性能优化
3. 可维护性 > 开发速度

【思考框架】
分析问题时请考虑:
- 是否符合 TypeDom 最佳实践？
- 是否遵循编码规范？
- 是否便于测试和维护？
```

---

### 技巧 2: 上下文链 (Context Chain)

**方法**: 构建上下文关联链

```
任务 A 的上下文
  ↓ (输出成为)
任务 B 的输入上下文
  ↓ (输出成为)
任务 C 的输入上下文

示例:
1. 项目分析 → 分析报告
2. 基于报告 → 重构方案
3. 基于方案 → 实施代码
```

---

### 技巧 3: 多 Agent 上下文传递

**场景**: 在不同角色间切换

```markdown
第一轮 [分析师]:
【角色】项目结构分析师
【任务】分析当前组件库结构
【输出】结构化报告

第二轮 [架构师]:
【角色】技术架构师
【输入】上一轮的分析报告
【任务】设计优化方案

第三轮 [开发者]:
【角色】高级开发者
【输入】上一轮的优化方案
【任务】实施具体代码
```
